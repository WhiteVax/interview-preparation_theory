### 1. Что такое индекс?
Индекс (staging area, «область подготовленных изменений») — промежуточная область между рабочей директорией и историей коммитов. В него попадает снимок тех изменений, которые войдут в следующий коммит. Благодаря этому можно подготовить к коммиту только часть файлов или отдельные фрагменты файла. Посмотреть состояние можно командой `git status`, подготовленное содержимое — `git diff --cached`.

### 2. Как добавить изменения в индекс? (`git add .`)
`git add <путь>` добавляет новые и изменённые файлы по указанному пути в индекс; например, `git add src/Main.java`. `git add .` добавляет изменения в текущем каталоге и его подкаталогах, а `git add -A` учитывает изменения и удаления во всём репозитории. Для выборочной подготовки фрагментов используют `git add -p`. Команда фиксирует текущее содержимое файла в индексе: последующие правки нужно добавить повторно.

### 3. Как сделать фиксацию изменений? (`git commit -m "text"`)
После подготовки нужных изменений выполните `git commit -m "Краткое описание"`. Коммит сохраняет снимок индекса в локальную историю и получает уникальный идентификатор; он также содержит ссылку на родительский коммит, автора и сообщение. Перед фиксацией полезно проверить `git diff --cached`. `git commit -am "..."` автоматически подготавливает изменения уже отслеживаемых файлов, но не добавляет новые неотслеживаемые файлы.

### 4. Как отправить изменения в удалённый репозиторий? (`git push origin master`)
`git push <remote> <branch>` отправляет коммиты локальной ветки в удалённый репозиторий, например `git push origin main`. При первом push ветки обычно используют `git push -u origin <branch>`: флаг `-u` связывает локальную ветку с upstream, после чего достаточно `git push`. Push может быть отклонён, если удалённая ветка содержит отсутствующие у нас коммиты; сначала нужно получить и интегрировать их. Не следует без необходимости переписывать общую историю через force push.

### 5. Как синхронизироваться с удалённым репозиторием? (`git pull origin master`)
`git pull <remote> <branch>` получает изменения и интегрирует их в текущую ветку: по умолчанию обычно через merge; `git pull --rebase` вместо этого перебазирует локальные коммиты поверх полученной истории. Команда должна выполняться в ветке, которую нужно обновить. `git fetch` только скачивает сведения и коммиты, не меняя текущую ветку, поэтому позволяет сначала проверить изменения. Если появились конфликты, их нужно разрешить, отметить файлы через `git add` и завершить merge или rebase.

### 6. Как создать ветку?
`git branch <имя>` создаёт ветку, но оставляет нас на текущей. Создать ветку и сразу перейти на неё можно командой `git switch -c <имя>` (или старым эквивалентом `git checkout -b <имя>`). Новая ветка указывает на текущий коммит; последующие коммиты в ней не меняют исходную ветку.

### 7. Как переключиться между ветками?
Для перехода на существующую ветку используют `git switch <имя>`; старый вариант — `git checkout <имя>`. Незакоммиченные изменения могут перейти вместе с нами, если это безопасно; при конфликте Git откажет в переключении, чтобы не затереть работу. Перед переключением проверьте `git status`, затем сохраните, закоммитьте или временно уберите изменения в stash.

### 8. Как отменить локальные изменения?
Сначала проверьте `git status` и `git diff`, поскольку отмена может удалить работу. Незастейдженные изменения файла можно убрать командой `git restore <файл>`, а изменения уже в индексе — `git restore --staged <файл>` (сам файл при этом останется изменённым в рабочей директории). `git restore --source=HEAD --staged --worktree <файл>` возвращает файл и в индексе, и в рабочей директории к HEAD. Для новых неотслеживаемых файлов есть `git clean`, но он удаляет файлы; сначала безопасно посмотреть результат с `git clean -n`.

### 9. Расскажи о команде `git reset`?
`git reset` перемещает указатель текущей ветки на другой коммит; режим определяет судьбу индекса и рабочей директории. `--soft` оставляет изменения подготовленными, `--mixed` (режим по умолчанию) сохраняет файлы, но очищает индекс, `--hard` приводит и индекс, и файлы к выбранному коммиту, удаляя соответствующие локальные изменения. Например, `git reset --soft HEAD~1` отменяет последний коммит, оставляя его изменения подготовленными. `git reset <файл>` убирает файл из индекса, не перемещая ветку. Для уже опубликованных коммитов обычно безопаснее `git revert`: он создаёт новый коммит, отменяющий изменения, вместо переписывания общей истории.

### 10. Расскажите о команде `git stash`.
`git stash` временно сохраняет незакоммиченные изменения и очищает рабочую директорию, чтобы можно было переключиться на другую задачу. `git stash push -m "описание"` сохраняет отслеживаемые изменения; `-u` включает также неотслеживаемые файлы. `git stash list` показывает сохранённые записи, `git stash apply` применяет запись, сохраняя её в списке, а `git stash pop` применяет и удаляет её при успешном применении. Возможны конфликты, которые нужно разрешить как обычно. Stash локален и не заменяет коммит или резервную копию.

### 11. Расскажите о команде `git cherry-pick`.
`git cherry-pick <коммит>` применяет изменения выбранного коммита к текущей ветке и создаёт новый коммит с теми же изменениями, но новым идентификатором и текущей веткой в качестве родителя. Команда полезна, когда нужно перенести отдельное исправление без слияния всей ветки. Если возникли конфликты, разрешите их, выполните `git add <файлы>` и `git cherry-pick --continue`; отменить операцию можно через `git cherry-pick --abort`. Перенос нескольких коммитов возможен диапазоном, но важно правильно выбрать границы.

### 12. Расскажите о команде `git rerere`. Как разрешаются конфликты?
`rerere` (reuse recorded resolution) запоминает, как разрешались конфликтные фрагменты, и может повторно применить такое же разрешение при следующем аналогичном конфликте. Включить функцию можно командой `git config --global rerere.enabled true` (или только для репозитория, опустив `--global`). При конфликте Git помечает конфликтующие области в файлах; нужно вручную отредактировать их, удалить маркеры `<<<<<<<`, `=======`, `>>>>>>>`, проверить результат, затем выполнить `git add` и завершить merge/rebase/cherry-pick соответствующей командой `--continue`. Rerere помогает повторно использовать решение, но его результат каждый раз нужно проверить: совпадающий фрагмент не гарантирует правильность для нового контекста.
